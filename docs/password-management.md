# Password management

POST /api/auth/forgot-password accepts Email and always returns the same successful message for unknown, locked or unconfirmed accounts. Eligible accounts receive a new 32-byte random reset token, stored only as SHA-256 PasswordResetTokenHash with 30-minute expiry. A request within one minute of issuance is suppressed. This is a per-account cooldown, not comprehensive rate limiting. New requests replace older tokens. Save happens before email delivery; there is no transactional email outbox, so delivery failure can require a retry after cooldown.

POST /api/auth/reset-password accepts AccountId, Token, NewPassword and ConfirmPassword. It checks account eligibility, token format/hash and expiry, BCrypt-hashes the new password, clears the token and temporary failed-login state, then saves once. It does not confirm an unconfirmed email or unlock a manually locked account. Invalid/expired/already-used tokens use the same business error.

POST /api/auth/change-password uses Authorize and account ID exclusively from validated JWT sub. It verifies OldPassword with BCrypt, checks the new password and rejects reuse of the current password, clears outstanding reset state and commits once. Password strings are preserved without trimming. Request contracts follow the current 8–64-character password policy.

Custom EF mapping adds PasswordHash, PasswordResetTokenHash and PasswordResetTokenExpiresAt as concurrency tokens. Reset conflicts become InvalidReset; change conflicts become ConcurrentChange (409). This also means other account mutations can conflict with password changes; existing login/refresh conflict handling is preserved. No generated EF, SQL or IUnitOfWork changes.

UI routes /forgot-password, /reset-password and /change-password share a small form component with separate email/new-password models. Login links to forgot-password; authenticated navigation links to change-password. Browser HTTP calls use AuthApiClient and existing coordinated AuthSession for authenticated change. No passwords or reset tokens go into credential storage. Form secrets are cleared on save/disposal. Reset token travels in a URL fragment, is read through password-reset.js and removed from the address bar; it is not prerendered or sent in the page GET URL. Reload after consumption requires reopening the link.

Email delivery currently follows the existing local-development simulation. DevelopmentPasswordResetSender logs a reset link ONLY when environment is Development and PasswordReset:WebOrigin is HTTPS localhost (default https://localhost:7012). This is a secret-bearing local test log. Replace the sender with real email delivery before deployment; the development sender throws outside Development. No production email provider/package is added.

Password changes and resets now revoke every unrevoked device and refresh token belonging to the target account, including the current browser. Password/token consumption and revocation use one SaveChanges inside an account-lock transaction. Existing JWTs and playback tickets are not blacklisted and may remain usable until expiry. Endpoint rate limiting and a real email provider remain future work. Local browser storage/XSS risks remain as previously documented. Public generic messages do not guarantee identical request timing. See account-session-revocation.md for locking and client coordination.

Tests: Playback.Specs covers normalized lookup, generic unknown-account response, cooldown, token expiry boundary, single use, BCrypt, exact password preservation, wrong old password, pending reset invalidation and EF concurrency metadata. These are fake-persistence checks, not a real SQL concurrency race or email/browser test.

Manual: request reset from login, open link from API terminal on https://localhost:7012, reset and log in with new password; reject old password, expired/reused/replaced link, locked/unconfirmed account and mismatched confirmation. Change password while logged in; test wrong old password, same new password, simultaneous submissions and navigation/logout during a request. Never paste real tokens or passwords into issue reports.
